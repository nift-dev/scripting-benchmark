Rules before results

Methodology

The benchmark is designed to discover Nift's performance, not manufacture a win.

Comparable work

Implementations preserve the same algorithm and asymptotic complexity while allowing natural language idioms. Inputs are deterministic and shared. Pathological implementations are rejected rather than used to make another runtime look slow.

Cold and warm are different questions

Process startup is benchmarked explicitly. Very short algorithmic workloads run repeated iterations inside one process so startup does not dominate execution measurements.

Measurements

Record wall time, CPU time, peak RSS, source lines/bytes, runtime versions, machine details and raw samples. Selected workloads use ordinary and enlarged inputs to expose both scripting-scale latency and sustained runtime behaviour.

Results contract

The website consumes generated JSON. Benchmark tooling owns the measurements; presentation code does not rewrite them.

No recursion requirement

Where traversal or orchestration can naturally use an explicit queue, benchmark harness scripts and practical scripting implementations should favour queues over recursion. Algorithm benchmarks whose subject is specifically recursion may still test recursion deliberately and label that fact.
